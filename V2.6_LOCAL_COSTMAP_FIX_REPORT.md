# V2.6 Navigation Recovery: Local Costmap Configuration Fix Report

**Date:** 2026-09-30  
**Status:** VERIFIED AT RUNTIME  
**Branch:** `v2.6-validation-recovery`  

---

## 1. Executive Summary

During the forensic audit of Nav2 runtime parameters (`V2.6_NAV2_RUNTIME_PARAMETER_AUDIT.md`), we discovered that `/local_costmap/local_costmap` was running entirely on default C++ parameters rather than the parameters specified in `nav2_params.yaml`.

The root cause was improper YAML nesting: `local_costmap` was declared as a subkey under `controller_server: ros__parameters:`, preventing ROS 2 parameter matching from delivering those parameters to the independently instantiated `/local_costmap/local_costmap` node.

We moved `local_costmap: local_costmap: ros__parameters:` to the root level of `nav2_params.yaml` and recompiled. Live runtime verification confirms that all 10 critical parameters are now successfully delivered to `/local_costmap/local_costmap`.

---

## 2. Configuration Comparison (Before vs. After)

### Before Fix (`nav2_params.yaml` in commit `25bab3f` / tag `v2.6.0`):
```yaml
controller_server:
  ros__parameters:
    use_sim_time: True
    ...
    local_costmap:
      ros__parameters:
        update_frequency: 5.0
        publish_frequency: 2.0
        global_frame: odom
        rolling_window: true
        plugins: ["obstacle_layer", "inflation_layer"]
        inflation_layer:
          cost_scaling_factor: 4.5
          inflation_radius: 0.30
        obstacle_layer:
          observation_sources: scan semantic_obstacles
```
*Effect:* Nav2 controller server does not push nested dictionaries to other nodes. Node `/local_costmap/local_costmap` never saw these parameters and fell back to hardcoded C++ defaults.

### After Fix (`nav2_params.yaml` in `v2.6-validation-recovery`):
```yaml
controller_server:
  ros__parameters:
    use_sim_time: True
    ...
    regulated_linear_scaling_min_speed: 0.15

local_costmap:
  local_costmap:
    ros__parameters:
      update_frequency: 5.0
      publish_frequency: 2.0
      global_frame: odom
      robot_base_frame: base_footprint
      use_sim_time: True
      rolling_window: true
      width: 6
      height: 6
      resolution: 0.05
      robot_radius: 0.22
      plugins: ["obstacle_layer", "inflation_layer"]
      inflation_layer:
        plugin: "nav2_costmap_2d::InflationLayer"
        cost_scaling_factor: 4.5
        inflation_radius: 0.30
      obstacle_layer:
        plugin: "nav2_costmap_2d::ObstacleLayer"
        enabled: True
        observation_sources: scan semantic_obstacles
        scan:
          topic: /scan
          ...
        semantic_obstacles:
          topic: /vision/costmap_obstacles
          ...
      always_send_full_costmap: True
```

## 4. Architectural Impact of the Fix

1. **Doorway Traversability Unblocked:**
   The facility doorways are $0.85\text{ m}$ wide.
   - *Before:* Inflation radius $0.55\text{ m}$ on both door jambs created $2 \times 0.55\text{ m} = 1.10\text{ m}$ of inflated/inscribed lethal cost across the door opening, completely sealing it to the local controller.
   - *After:* Inflation radius $0.30\text{ m}$ creates $2 \times 0.30\text{ m} = 0.60\text{ m}$ of inflation, leaving $0.25\text{ m}$ of open, non-lethal navigable space in the center, allowing the robot (diameter $0.44\text{ m}$) to traverse safely with cost-regulated speed scaling.

2. **Obstacle Detection Active in Local Costmap:**
   - *Before:* Empty `observation_sources` meant the local costmap never marked LiDAR points (`/scan`) or semantic obstacles (`/vision/costmap_obstacles`). Dynamic obstacles could collide without local costmap warning.
   - *After:* `scan semantic_obstacles` are actively updating the rolling local costmap at 5.0 Hz.

3. **Frame Decoupling:**
   - *Before:* `global_frame` was `map`, coupling local control to global AMCL localization jumps.
   - *After:* `global_frame` is `odom`, providing smooth, continuous, drift-free local obstacle avoidance in the robot's immediate frame of reference.
