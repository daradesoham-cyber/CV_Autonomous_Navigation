# V3.0 Technical Documentation: Hospital Logistics Robot

V3.0 is a simulated autonomous logistics robot in a realistic hospital. It picks up a blood-sample carrier in the
West Ward and delivers it to the laboratory, sharing the corridors with moving staff, visitors and a trolley.
This document covers the architecture, every runtime component, the data, the dashboard and API, how the generated
assets are rebuilt, and how the system is tested.

## 1. System overview

```
           │ robot (DiffDrive, camera 640x480, 2D LiDAR 720 rays / 12 m, IMU)          │

                           │                                          │ set_pose (traffic)
   ┌───────────────────────▼───────────┐   ┌──────────────────┐   ┌──┴──────────────────┐
   │ Perception                        │   │ Localization     │   │ v3_traffic_* (x4)   │
   │ v3_detection_node (YOLOv8n, GPU)  │   │ map_server+AMCL  │   │ staff/visitors/     │

   ┌──────▼───────────────▼───────────────────────────▼───────┐
   │ Navigation: decision_engine_node (topological routing,    │──NavigateToPose──► Nav2
   │ learned history, signs, TTC yield, replans)               │                    (planner, controller,
   └──────────────────────────▲────────────────────────────────┘                     behaviors, BT navigator)
                              │ /navigation/goal_label, control
   ┌──────────────────────────┴───────────┐    ┌──────────────────────────────────────┐
   │ v3_mission_manager (state machine,   │◄───┤ v3_web_server (Flask, port 8080)      │◄── browser (dashboard)
   │ mission DB, e-stop latch)            │───►│ /api/state, /api/mission, camera ...  │
```

Everything is launched by `ros2_ws/src/hospital_logistics/launch/v3_full_system.launch.py`, which `V3/scripts/start_v3.sh`
calls. The launch is staggered: the world at 0 s, localization, Nav2 and the decision engine at 6 s, then perception,
mission manager, traffic and UI at 14 s.

## 3. Hospital environment

- **Source:** AWS RoboMaker Hospital World (branch `ros2`, commit `7161eb8`, MIT-0). The furniture and people are 43
  OpenRobotics Gazebo Fuel models (CC-BY 4.0). Details are in `V3/V3_NEW_HOSPITAL_SOURCE.md`, with attribution in
  `V3/hospital/models/ATTRIBUTION.md`.
- **Building:** a single floor, 25 × 56 m. It contains the main entrance and elevator lobby, the main lobby with the
  reception desk, two waiting areas, the nursing station, patient rooms in both wings, the west and east wards with
  curtained beds, restrooms, a surgery/X-ray (diagnostics) block, a recovery bay, a staff lounge, storage, a pharmacy
  and the laboratory.
- **World file:** `V3/worlds/v3_hospital_world.sdf`, generated by `V3/scripts/build_aws_hospital_world.py`.
  - The Gazebo Classic world is converted to Gazebo Sim 10 (Sim system plugins, 200 Hz physics, flattened
    includes, offline Fuel URIs, static props).
  - The ceiling is left out so the GUI shows the plan from above; point lights replace the ceiling lights.
  - The AWS floor mesh is visual-only and the robot drives on a flat ground plane. Wheel slip on the floor mesh had
    made odometry read 1.52× the true distance.
  - Three upstream props that were saved at z = −7.6e8 are restored to the floor, and the trolley bed is parked
    clear of the east corridor.
- **V3 additions** (`V3/scripts/v3_hospital_additions.py`):
  - a furnished laboratory: benches with microscope and centrifuge, cabinets, drawers, a storage rack, an
    instrument cart and a BP monitor;
  - the collection table with the payload carrier;
  - the COLLECTION and LABORATORY TEST POINT plaques;
  - 10 directional signs (LABORATORY, DIAGNOSTICS, NURSING STATION, RECEPTION, WARD, TESTING, PHARMACY), in the
    V2.6 sign style so the YOLO `directional_sign` class applies;
  - the 4 traffic models.

## 4. Map, topology and logistics locations

All coordinates are in the map frame, which is the Gazebo world frame, in metres.

### Occupancy map
- **File:** `V3/maps/v3_hospital_map.yaml` / `.pgm`. Resolution 0.05 m, 543 × 1181 px, 27.1 × 59.0 m, origin (−13.57, −36.07).
- **Generation:** `V3/scripts/generate_hospital_map.py` slices every collision mesh of the world at 0.10 m and 0.27 m
  (the LiDAR plane) and rasterises the result. It honours Collada `<unit>` (the AWS meshes are in centimetres) and
  excludes the moving traffic models.
- **Accuracy:** a live LiDAR scan placed at the ground-truth pose lies on average 0.023 m from the map walls.

### Topology (single source: `V3/scripts/v3_hospital_layout.py`)
- 33 nodes (destinations, junctions, waypoints, doors) and 37 undirected edges.
- **Corridors and junctions:** the west corridor (x = −5) and east corridor (x = +5) run north–south. They are joined
  by three cross corridors (y = −8.5, −14.5, −24.5) and the main lobby, so most destinations have several routes.
- **Validation:** `V3/scripts/validate_hospital_topology.py` checks that every node is free and every edge is
  connected at robot radius 0.27 m, using a grid path no longer than max(1.6 × straight-line length,
  straight-line length + 3 m). Result: 33/33 nodes free, 37/37 edges connected (`V3/docs/evidence/new_hospital/topology_check.png`).
- **Database:** `V3/scripts/build_v3_hospital_topology.py` writes the topology database
  `V3/data/v3_hospital_navigation_memory.db` (fresh history), the sign map `V3/config/v3_hospital_semantic_map.yaml`
  and the mission locations `V3/config/logistics_locations.yaml`.

### Logistics locations

| Location | Node | Position | Notes |
|---|---|---|---|
| Spawn / Main Entrance | `entrance` area | (0, 13), facing south | Robot start pose |
| **Collection point** | `collection_point` | (−8.5, −15.6) | West Ward aisle, at the bedside table with the payload and the COLLECTION plaque |
| **Laboratory / Test point** | `laboratory` | (8.6, 14.6) | NE laboratory, facing the bench with the TEST POINT plaque |
| Reception, Nursing Station, Storage, Pharmacy, Diagnostics, East Ward, Recovery, Waiting, Patient Rooms, Staff Lounge | see `logistics_locations.yaml` / layout | | Also selectable as mission endpoints |

Default route: West Ward → West Ward door → west corridor (south, mid and north intersections) → main lobby →
laboratory door → laboratory test point.

## 5. Robot and sensors

The robot is unchanged from V2.6/V3 (`ros2_ws/src/autonomous_robot_description`):
- **Base:** differential drive; footprint radius 0.22 m; wheel radius 0.06 m; separation 0.35 m; cruise speed 0.5 m/s.
- **Camera:** 640 × 480, horizontal FOV 1.15 rad, ~28 Hz.
- **LiDAR:** 720 rays, 12 m range, 20 Hz, mounted at 0.27 m.
- **Other:** IMU, and wheel odometry from the DiffDrive system.

## 6. Perception

- **Detection:** `v3_detection_node` runs `V3/models_trained/v3_yolov8n_from_v25.pt` (YOLOv8n; classes: person,
  hospital_bed, cart, wheelchair, iv_stand, surgical_trolley, directional_sign, collection_point_marker,
  lab_test_point_marker) on CUDA. Confidence threshold 0.35, ~28 Hz, ~20 ms total per frame.
- **Detection in the new hospital** (9,314 frames, without retraining), mean confidence per class:

  | Class | Mean confidence |
  |---|---|
  | person | 0.80 |
  | directional_sign | 0.76 |
  | iv_stand | 0.74 |
  | wheelchair | 0.73 |
  | surgical_trolley | 0.69 |
  | cart | 0.65 |
  | hospital_bed | 0.64 |
  | collection_point_marker | 0.46 |
  | lab_test_point_marker | 0.44 |

- **Signs:** each `directional_sign` box is matched to a physical sign in `v3_hospital_semantic_map.yaml`, using the
  robot pose, the sign's facing direction, the field of view and the bearing. The confirmed text and direction are
  published on `/vision/signs`.
- **Fusion:** `v3_spatial_fusion_node` associates each box with LiDAR returns inside its bearing window, with motion
  compensation.
  - `range_source = lidar`: a metric position in the robot frame.
  - `ground_plane`: an estimate from the box bottom.
  - `visual_only`: no range.
  - Only LiDAR-ranged objects feed the world-frame tracker, TTC (`/vision/ttc`) and the semantic obstacles. The
    dashboard shows a distance only for LiDAR-ranged objects; signs and markers are never shown with a distance.
- **Costmap obstacles:** `v3_costmap_obstacle_node` turns semantic obstacles into `/vision/costmap_obstacles` for the
  Nav2 local and global obstacle layers.

## 7. Navigation

- **Nav2** (`V3/config/v3_nav2_params.yaml`, a copy of the V2.6 parameters):
  - AMCL (likelihood field, 600–2500 particles), with the initial pose at the spawn point.
  - Random-particle recovery is disabled (`recovery_alpha_fast/slow = 0`). In the symmetric wings it caused
    wrong-wing relocalisation jumps.
  - NavFn planner, Regulated Pure Pursuit controller (0.5 m/s), inflation 0.30 m, goal tolerance 0.35 m.
- **Decision engine:** `autonomous_robot_navigation/decision_engine_node.py`, run through
  `hospital_logistics/v3_decision_engine.py`.
  - It receives a destination label and computes candidate routes on the topology graph.
  - It sends the route node by node to Nav2.
  - It monitors progress, signs, obstacles and TTC, and replans when needed (`DYNAMIC_OBSTACLE`, `NO_PROGRESS`,
    `NAV2_ABORT`, `LOW_CLEARANCE`, …).
- **V3 adapter fixes:**
  1. adds the missing `ReplanReason.OBSTACLE_BLOCKED`;
  2. records successful traversals in the route segments, so learning works in both directions;
  3. **ignores non-moving obstacles that lie on occupied cells of the static map.** In the furnished hospital these
     are parked beds, seated visitors and so on; Nav2 already plans around them. Before this change the first
     mission had 7 replans and 154 m; after it, 0 replans and 107 m.
- **Route cost** (per directed segment, `topological_graph.Edge.calculate_cost`):
  ```
  cost = distance + 3.5·obstacle_density + 5·(failures + 2·(1 − reliability)) + 2.5·1.5[narrow/door]
         + 0.5·travel_time − min(0.12·traversals, 0.25)·distance          (blocked edge: 1e6)
  ```
  The engine picks the route with the lowest summed cost. Its statistics are stored in
  `v3_hospital_navigation_memory.db` (tables `route_segments`, `traversals`, `obstacles`, `replan_events`) and shown
  in the dashboard's Path Learning view.

## 8. Mission manager

`hospital_logistics/v3_mission_manager_node.py`:
- **States:** `IDLE → READY → GO_TO_COLLECTION → AT_COLLECTION → PAYLOAD_SECURED → GO_TO_LAB → AT_LAB → MISSION_COMPLETE`,
  plus `PAUSED`, `CANCELLED`, `FAILED` and `EMERGENCY_STOP`.
- **READY** requires an AMCL pose, the decision engine, the Nav2 `navigate_to_pose` server, and fresh YOLO and fusion
  output.
- **Commands** (`/v3/mission/command`, JSON; whitelist `start pause resume cancel reset estop`):
  - start with `source` / `destination` (any location in `logistics_locations.yaml`);
  - pause and cancel cancel the Nav2 goal;
  - estop latches: it cancels Nav2 every 0.2 s, sends ABORT to the decision engine every second and holds a zero
    twist at 20 Hz until reset.
- **Timings:** collection and delivery dwell 3 s each; leg timeout 300 s of active time. A marker detection in the 15 s
  before arrival is recorded as visual confirmation; it is informational only, and the map pose decides arrival.
- **History:** each mission is written to `V3/data/v3_hospital_missions.db` (result, legs with routes and
  decision-engine events, path, distance, duration, minimum LiDAR range, replans, TTC events, sign decisions).

## 9. Hospital traffic

Four `v3_traffic_node` instances move Gazebo models kinematically (`set_pose` at 10 Hz). The lines are defined in
`v3_hospital_layout.TRAFFIC`:

| Model | Movement |
|---|---|
| `dynamic_person` (nurse) | Crosses the west corridor at y = −18.5 (on the mission route) |
| `dynamic_person_2` (visitor) | Walks north–south across the west lobby (crosses lobby ↔ lobby_west and reception → west corridor) |
| `dynamic_hospital_trolley` | Crosses the east corridor at y = −1.0 |
| `dynamic_person_3` (visitor) | Crosses the east corridor at y = −19.5 |

How the traffic behaves:
- Every line crosses a corridor segment that carries no east–west topology edge. Kinematic motion along the robot's
  lane can shove the robot and corrupt its odometry.
- Each model waits while the robot is within 1.6 m of its next step, steps back when the robot is closer than 1.0 m,
  and turns back after 6 s of mutual yielding.
- Traffic is off by default. Toggle it in the dashboard, publish `/simulation/enable_dynamic_obstacles`, or use
  `start_v3.sh --traffic`.

## 10. Dashboard and web API

The dashboard is `V3/ui/index.html`: a single file in vanilla JS with no external dependencies, so it works on a
LAN without internet. It is served by `v3_web_server` on `0.0.0.0:8080`. Only loopback and private (RFC 1918 /
link-local) clients are accepted; other clients get HTTP 403.

| View | Shows |
|---|---|
| Operations | Map (zoom, pan, pinch, follow robot; layers for topology and LiDAR), robot pose and heading, planned route (only while a mission runs), travelled path, collection and laboratory markers, location labels, LiDAR points, fused obstacles; live camera with YOLO boxes and rates; mission control with stepper, progress and Start/Pause/Resume/Cancel/Reset; traffic toggle; robot status strip; operator-attention banner |
| Perception | Camera, object list (class, confidence, LiDAR range or *not ranged*, robot-frame x/y, bearing), polar LiDAR plot with camera FOV, ranged associations and bearing-only rays |
| Navigation | Current goal, route chain with progress, decision-engine state, route cost and reliability, replans and last reason, TTC, clearances, cost terms, filtered event log (decision engine + mission) |
| History | Stored missions with filter (result/source/destination/text) and sortable columns; detail with legs, routes, events and a mini-map of the stored path |
| Path Learning | Per-segment length, uses, successes, failures, reliability, obstacles, replans, route cost and flags; usage map; stored replan reasons; explanation of the cost model |
| System | Online / Starting / Error / Offline / Unavailable for Gazebo, camera, LiDAR, odometry, AMCL, YOLO, fusion, costmap obstacles, Nav2, decision engine, mission manager, UI backend and battery (unavailable: no source); live ROS node list |

**E-STOP:** the header button sends the existing `estop` command. Shift+Space is a keyboard shortcut for the same
command. The button shows **E-STOP LATCHED** until Reset.

### REST API

| Endpoint | Method | Returns / does |
|---|---|---|
| `/` | GET | Dashboard |
| `/api/state` | GET | Aggregated live state: `system` (topic rates and ages), `robot` (pose, twist, nearest LiDAR), `mission` (mission manager state, locations, events), `navigation` (route, cost, clearances, TTC, replans), `perception` (fused objects, timing), `nav_events`, `ros_nodes`, `ui_backend` |

## 12. Operating the system

See `V3/V3_FINAL_RUNBOOK.md`. In short:
- **Start:** `V3/scripts/start_v3.sh [--headless] [--traffic] [--no-browser] [--port N]`, or the desktop icon.
  READY takes about 30 s.
- **Stop:** `V3/scripts/stop_v3.sh`. Restart: `V3/scripts/restart_v3.sh`.
- **Health check:** `V3/scripts/health_check.sh`.
- **Reset the learned history:** with V3 stopped, run `.venv/bin/python V3/scripts/build_v3_hospital_topology.py`.
  This re-creates the topology database with empty history.

## 13. Rebuilding generated assets

Only needed after changing the layout or the world. Use the project venv (`.venv/bin/python`).

| Change | Command |
|---|---|
| Locations, edges, signs, plaques, traffic (`v3_hospital_layout.py`) | `build_aws_hospital_world.py` → `generate_hospital_map.py` → `validate_hospital_topology.py` → `build_v3_hospital_topology.py` |
| Props, lab furniture, lights (`v3_hospital_additions.py`) | `build_aws_hospital_world.py` → `generate_hospital_map.py` → `validate_hospital_topology.py` |

`build_aws_hospital_world.py` needs the upstream sources in `V3/third_party`. To fetch them:
```bash
git clone -b ros2 https://github.com/aws-robotics/aws-robomaker-hospital-world V3/third_party/aws-robomaker-hospital-world
(cd V3/third_party/aws-robomaker-hospital-world && git checkout 7161eb8448f5cba6a469da7a79ae5d660b0b7f58)
```

## 15. Known limitations

- **Startup crash:** `ros_gz_bridge` occasionally segfaults at startup (about 1 in 12 starts). `start_v3.sh`
  reports "not READY" and stops; a restart fixes it.
- **Marker confidence:** the logistics marker plaques are detected at about 0.45 confidence. Arrival is decided by the
  map pose, so this does not affect missions.
- **Sign routing:** sign direction does not change routing. The topology route is the authority, and signs confirm it.
- **Install path:** the world file refers to the sign and plaque textures by absolute path under
  `~/CV_Autonomous_Navigation`. Install the project there, or rebuild the world after moving it.
- **Camera overlay:** the camera stream overlay is drawn by the backend at 8 fps.
- **Moving objects on the map:** moving and static fused objects are not distinguished on the map.
- **Dataset scripts:** the dataset and training scripts (`V3/datasets`, `V3/training`) document how the current YOLO
  model was trained in the previous V3 world. They are historical and not used at runtime.
