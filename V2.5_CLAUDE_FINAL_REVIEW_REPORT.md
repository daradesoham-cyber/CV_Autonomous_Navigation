## 5. Navigation Bottleneck — Root Cause Analysis

> **User directive: "DO NOT ACCEPT THIS CONCLUSION WITHOUT EVIDENCE."**

### 5.1 Gemini's claim
"Nav2 local trajectory clearance / low speeds (0.15–0.25 m/s) in narrow corridors."

### 5.2 What the data actually shows

**Evidence from `v24_mission_validation_results.json`:**

**Group 1 — Near-zero progress missions (M1, M6, M9):**
- M1: 2.99m / 52 replans / 12 yields / 0.28m clearance
- M6: 6.72m / 50 replans / 17 yields / 0.29m clearance
- M9: 2.81m / 43 replans / 7 yields / 0.30m clearance

These three missions start in the **hospital ward area**. Min clearance of 0.28–0.30m is dangerously low and triggers continuous recovery behavior (line 571 in decision_engine_node.py):
```python
if self.front_clearance < self.recovery_params['min_clearance_recovery_threshold'] or self.min_clearance < 0.16:
    self._trigger_recovery(ReplanReason.LOW_CLEARANCE)
```
With `min_clearance_recovery_threshold = 0.22m` and actual clearance at 0.28–0.30m, recovery isn't being triggered by the threshold — but the LiDAR costmap still sees obstacles at 0.28m causing Nav2 to replan. The 50–52 replans in 180s (≈1 replan every 3.5s) indicate the robot is continuously finding its planned path blocked and replanning, not making net progress.

**Root cause for M1/M6/M9:** The hospital ward area has **structural narrow corridors** combined with the dynamic forklift/cart patrol that constantly blocks the only viable path. The DYNAMIC_OBSTACLE replan reason appears in all three. The robot is caught in a replan cascade: path computed → dynamic obstacle appears → replan → same obstacle still there → replan → ...

This is **partially a Nav2 controller issue** (inflation radius 0.38m in a 0.28m clearance corridor leaves no valid trajectory) but is **also a topological graph issue**: the decision engine keeps sending Nav2 to the same blocked path because alternative routes through the narrow ward are also blocked.

**Group 2 — Progressing but timeout missions (M3, M5, M7, M8, M10):**
- M3: 39.02m / 21 replans / 3 yields
- M5: 45.47m / 13 replans / 20 yields
- M7: 35.60m / 14 replans / 7 yields
- M8: 34.54m / 22 replans / 7 yields
- M10: 30.49m / 35 replans / 14 yields (220s timeout!)

These missions made substantial progress. The timeout is genuine: at average travel speeds, 30–45m in 180s is achievable only if the robot moves continuously at ~0.16–0.25 m/s with minimal stops. Nav2 `desired_linear_vel: 0.5 m/s` but actual achieved speed is significantly lower due to costmap-regulated velocity scaling.

**Nav2 `nav2_params.yaml` analysis:**
```yaml
FollowPath:
  plugin: "nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController"
  desired_linear_vel: 0.5        # target velocity
  use_cost_regulated_linear_velocity_scaling: true   # slows near obstacles
  regulated_linear_scaling_min_speed: 0.1           # never below 0.1 m/s
  use_collision_detection: true
  max_allowed_time_to_collision_up_to_fast_stop: 2.0
```
The Regulated Pure Pursuit Controller with `use_cost_regulated_linear_velocity_scaling: true` will slow to 0.10–0.15 m/s in areas with high costmap values (near walls, obstacles). In a 1.8–2.4m wide corridor with inflation_radius=0.38m, **the entire corridor is elevated cost**, causing constant velocity scaling.

**TTC contribution analysis:**
- 95 yields × 1.8s pause = **171 seconds** of stationary time across all 10 missions (~17s per mission average)
- M5: 20 yields × 1.8s = 36s stationary just from TTC
- M6: 17 yields × 1.8s = 30.6s stationary from TTC (in a 6.72m mission — extremely significant)

## 6. TTC Analysis

**95 yields across 10 missions:**
- M2: 0 yields (highest min TTC: 2.36s — obstacle never within threshold)
- M5: 20 yields (most — STORAGE→OFFICE crosses dynamic patrol routes)
- M6: 17 yields (hospital ward — tight space + patrol)

**Are the remaining 95 yields legitimate?** Gemini claims yes (genuine physical dynamic obstacles). Without live runtime observation I cannot independently verify every TTC event, but the min TTC values (0.15s–0.30s in high-yield missions) indicate genuine close-proximity events. The 2.36s min in M2 (0 yields) confirms the threshold correctly did not fire in a safe mission.

**Threshold analysis:** `yield_threshold_sec: 1.8s` appears appropriate. M2 at 2.36s min TTC correctly did not yield. The 0.15–0.30s min TTC events in other missions are genuine collision-course events.

**Recovery speed concern:** Each TTC yield pauses the robot for `yield_duration_sec: 1.8s`. This is equivalent to 1 full yield cycle per event. If a dynamic obstacle remains in path after the yield, the next TTC event fires again. This could create chains of yields. In M6 (17 yields × 1.8s = 30.6s) with only 6.72m traveled, TTC yield chains are likely contributing to the replan cascade.

**Recommendation (not implementing):** Consider reducing `yield_duration_sec` from 1.8s to 1.0s. The current value is calibrated to the yield threshold itself, which is unnecessarily symmetric. A shorter yield gives the robot time to reassess without locking out navigation for as long.
