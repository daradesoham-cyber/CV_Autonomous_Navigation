## 1. Overview & Objectives

The **V2.3 Navigation Upgrade** establishes a destination-aware, corridor-constrained topological navigation hierarchy. Instead of treating navigation as isolated coordinate goals or unconstrained straight lines across open space, the system structures the 35m × 30m warehouse facility into architectural corridors, junctions, semantic destinations, and dead-end zones.

### Core Architectural Hierarchy:
```
USER SELECTS DESTINATION (e.g. "STORAGE" / "HOSPITAL" / "ROOM A")
                          ↓
SEMANTIC DESTINATION DATABASE (config/semantic_destinations.yaml)
                          ↓
DESTINATION GRAPH NODE & APPROACH WAYPOINT
                          ↓
GLOBAL TOPOLOGICAL ROUTE (Multi-Criteria A* Planner)
                          ↓
WAYPOINT SEQUENCE VALIDATION (Corridor Boundary & Free Space Checks)
                          ↓
NAV2 LOCAL NAVIGATION (Regulated Pure Pursuit Controller)
                          ↓
CAMERA SIGN & DYNAMIC OBSTACLE MONITORING
                          ↓
GOAL APPROACH & DESTINATION ARRIVAL
```

## 3. Destination → Graph → Waypoint → Nav2 Execution

When a destination command is received via REST (`POST /api/goal {"goal": "storage"}`) or user click on the interactive dashboard:

1. **Resolution:** The decision engine queries `semantic_destinations.yaml` to identify the destination object, its entry approach node (`storage_approach`), and target pose `(-6.50, 3.00, 1.5708)`.
2. **Topological Global Routing:** The multi-criteria A* solver evaluates all non-blocked corridors between the robot's current nearest node and the destination node, computing $K=3$ candidate paths.
3. **Sequential Waypoint Dispatch:** Instead of commanding a direct leap across the map, the robot progresses through each intermediate junction node. Nav2 navigates segment-by-segment:
   - `start` $\implies$ `reception` $\implies$ `junction_1` $\implies$ `central_spine_1` $\implies$ `junction_7` $\implies$ `storage_approach` $\implies$ `storage`.
4. **Tolerance & Orientation Alignment:** As the robot approaches the final waypoint, the decision engine aligns the robot chassis to the destination's specified `world_yaw` for precise docking.

## 4. Corridor-Aware Waypoint Validation

Before forwarding any waypoint coordinate to Nav2's `NavigateToPose` action client:
- **Free Space Check:** Coordinate is cross-referenced with the static map grid to ensure $cost < 200$ (avoiding walls and structural pillars).
- **Corridor Centering:** If a waypoint drifts within 0.35m of an interior wall, the waypoint is dynamically projected back to the corridor centerline.
- **Reachability Gating:** A waypoint cannot be commanded if the direct line-of-sight from the previous node crosses an occupied costmap cell.
- **Log Events:** When a waypoint is adjusted, the event `CORRECTED_WAYPOINT (offset=0.22m)` is recorded.

## 5. Map Label Overlap Fix (Collision Box Resolution Algorithm)

In earlier iterations, destination and dead-end labels rendered directly adjacent to nodes, overlapping when nodes were close together.

### Implemented Algorithm:
In `ros2_ws/src/autonomous_robot_navigation/web/index.html` (`renderMap()`):
1. **Pass 1:** Renders all topological node dots.
2. **Pass 2:** Renders visual signpost pins at semantic destination coordinates.
3. **Pass 3:** Renders destination and dead-end badges with **4-candidate collision box resolution**:
   - For each label, computes text width + padding.
   - Evaluates 4 candidate bounding boxes: **Right** `(p.x + 9, p.y - 7)`, **Top** `(p.x - w/2, p.y - 20)`, **Bottom** `(p.x - w/2, p.y + 9)`, and **Left** `(p.x - w - 9, p.y - 7)`.
   - Checks overlap against `placedBoxes` array.
   - Selects the first collision-free candidate.
   - Draws a semi-transparent rounded pill background (`rgba(6, 78, 59, 0.88)` for destinations, `rgba(127, 29, 29, 0.88)` for dead ends), a leader line if offset, and crisp white font (`#ffffff`).

**Result:** Zero overlapping text across the entire facility map, even in dense corridor clusters.

- **Raw Sensor View:** Displays the unadulterated 15 Hz camera stream (`/api/camera_frame?view=raw`).

The stream automatically updates at 5 Hz in the dashboard via an optimized JPEG buffer pipeline.
